# A05-R2 — atomicidad de archivos y respuesta de validación

BASE_SHA=`194d3410bb64ee2dd7f77701a1fcb275d6c4992e`

R2 cierra **dos** defectos residuales directos de R1. Sin migraciones, sin dependencias, sin A06.

---

## 1. FILE CLEANUP MUST NEVER DELETE AN EXISTING VALID FILE

### Defecto verificado

`DocumentFileStore` y `PlanillaFileStore` usaban el SHA-256 como nombre físico:

```
clients/{client_id}/{sha256}.{ext}
sheets/{sheet_id}/{sha256}.{ext}
```

Dos subidas con bytes idénticos compartían la misma ruta física. Si la segunda fallaba en la persistencia del metadato, la limpieza (`disk->delete($relative)`) borraba el archivo que la primera subida seguía necesitando.

### Solución

Cada subida recibe un nombre físico **único aleatorio (UUID)**, mientras el SHA-256 se conserva como metadato de integridad:

```
clients/{client_id}/{uuid}.{ext}
sheets/{sheet_id}/{uuid}.{ext}
```

Archivos modificados:
- `app/Domain/Documents/DocumentFileStore.php`
- `app/Domain/Planillas/PlanillaFileStore.php`

### Outer-transaction cleanup (segunda mitad del mismo invariante)

`RespondToDocumentRequest` escribe el archivo dentro de la transacción BD, pero si una operación posterior (auditoría, cambio de estado de la solicitud) lanza, la BD hace rollback y el filesystem no.

Con nombres físicos únicos, la compensación es segura: en el `catch` exterior se elimina **solo** el archivo recién escrito para ese documento.

Archivo modificado:
- `app/Domain/Documents/Actions/RespondToDocumentRequest.php`

### Pruebas requeridas

- **F1**: subida idéntica por endpoint de personal falla → archivo original intacto
- **F2**: prueba análoga para `PlanillaFileStore`
- **F3**: rollback de transacción exterior en portal → solo el archivo nuevo se borra

Ubicación: `tests/Feature/A05/DocumentPortalFlowTest.php` (tests F1, F2, F3)

## 2. VALIDATE RESPONSE MUST REPORT THE AUTHORITATIVE STATUS

### Defecto verificado

`ValidateSheetToReady` lee y escribe bajo lock (modelo autoritativo), pero `PlanillaController::validate()` respondía con el modelo enlazado por la ruta (stale):

```php
'status' => $planilla->status->value  // ← stale
```

Una petición exitosa podía devolver `valid=true` y `status=draft` mientras en BD el estado era `ready`.

### Solución

Refrescar el modelo antes de construir la respuesta:

```php
$planilla->refresh();
return response()->json($result->toArray() + ['status' => $planilla->status->value]);
```

Archivo modificado:
- `app/Http/Controllers/Api/PlanillaController.php`

### Prueba requerida

Extender P1: tras `POST /api/planillas/{id}/validate` afirmar **ambas**:
- `valid == true`
- `status == ready`

Ubicación: `tests/Feature/A05/PlanillaEditTest.php` (test P1 extendido)
