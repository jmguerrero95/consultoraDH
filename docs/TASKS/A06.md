## 1. Qué entrega

A06 añade la capa de comunicación y automatización alrededor del sistema
operacional que ya existía:

| Área | Qué hace |
|---|---|
| **Centro de soporte** | Conversaciones persistentes con colas, asignación, prioridad, ciclo de vida, notas internas, SLA, adjuntos, audio |
| **Tiempo real** | Laravel Reverb self-hosted, canales privados/presencia, reconnect/resync, unread server-authority |
| **Correo bidireccional** | Fallback email cuando el destinatario está offline; ingreso HMAC-protegido; tokens Reply-To; cuarentena para correo ambiguo |
| **PWA + Web Push** | Manifest, service worker (sin cache de APIs autenticadas), VAPID, suscripciones por usuario |
| **Telegram admin** | Bot API, endpoints configurables, alertas SLA/automatización, test message |
| **Motor de automatizaciones** | Reglas por evento/fecha, vocabulario cerrado, cursor idempotente, ejecución con re-check de permisos |

## 2. Decisiones que conviene conocer

### 2.1 El «otro» operador existe, y no se adivina el operador

El operador se elige a mano y nunca se deduce de la empresa: la vía de radicación de
una empresa no es derivable de sus datos. `other` exige escribir un nombre, porque
«otro» sin nada detrás no registra nada.

### 2.2 Las líneas de la conversación son una fotografía, no una vista

Si los mensajes se derivaran en vivo, corregir un nombre reescribiría silenciosamente
cada conversación histórica. Los mensajes son una copia tomada una vez, con los
identificadores de origen para poder rastrearla.

### 2.3 El resumen de integridad es la bisagra entre vista previa y creación

Una vista previa se muestra a alguien y la creación llega segundos después. Si el
camino de creación recalculara el estado sin comprobar, ambos podrían describir
estados distintos. Por eso la vista previa devuelve un resumen; la creación
recalcula dentro del bloqueo y compara: si no coincide, responde 409 y no escribe
nada.

### 2.4 Email fallback es best-effort, nunca transaccional

Si el destinatario está offline, se encola un email de fallback. Si el email falla,
el mensaje de soporte **persiste igual**. La entrega es reintentable e idempotente.

### 2.5 Reply-By-Email es determinista, nunca adivinatorio

Un token Reply-To mapea **exactamente** a una conversación y participante. Si el
token falta, expira, o el remitente no coincide con el participante esperado →
cuarentena. Nunca se asocia un email entrante a un cliente solo porque
`from == client.email`.

### 2.6 Unread es monotonía, no contador optimista

El cursor `last_read_message_id` solo avanza. Una pestaña vieja que pida marcar
como leído un mensaje anterior **no mueve el cursor hacia atrás**. El unread del
portal excluye notas internas; el unread de staff excluye colas sin acceso.

### 2.7 Audio es adjunto normal

`MediaRecorder` en el navegador → WebM/Opus → almacenamiento privado → `<audio
controls>` nativo. No hay autoplay, no hay framework de audio pesado.

### 2.8 Telegram es solo alerta admin

No es canal de cliente. No se espeja la conversación. Mensajes esparcidos,
enrutados por endpoint configurado.

### 2.9 Automatizaciones son vocabulario cerrado

No hay código libre, no SQL, no shell, no webhooks arbitrarios. Triggers:
`audit_action`, `schedule`, `task_due`, `document_request_due`,
`receivable_overdue`, `support_sla_breach`. Actions: `internal_notification`,
`create_task`, `send_email`, `send_telegram`, `assign_support_queue`,
`assign_support_user`, `set_support_priority`. Cada acción re-valida permisos
del owner al ejecutar.

### 2.10 El cursor de auditoría evita duplicados

Para triggers `audit_action`, el cursor `automation_rule_cursors` persiste el
último `audit_event.id` procesado. Un crash/retry no pierde ni duplica acciones.

### 2.11 Fallo parcial no repite lo exitoso

Una regla con N acciones: si la 3 falla, el retry reintenta solo la 3. La 1 y 2
(ya `succeeded`) no se repiten. No hay duplicación de tareas/emails/telegrams.

  ni la estrategia de hosts de confianza

  almacenamiento privado; el escaneo de malware es de A07
