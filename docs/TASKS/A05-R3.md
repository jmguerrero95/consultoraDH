## 1. TRANSACTION OUTER FILE COMPENSATION

### Defecto verificado

`RespondToDocumentRequest` tenía el `catch` de compensación **dentro** del callback de
`DB::transaction`. Eso maneja fallos antes de que el callback retorne, pero **no** un
fallo lanzado por `DB::transaction()` al hacer **COMMIT** después de que el callback ya
retornó.

Invariante requerida:

```
archivo escrito con éxito
+
transacción BD NO hace commit exitoso

=> archivo físico recién escrito NO debe sobrevivir
```

### Solución

La compensación envuelve la llamada **completa** a `DB::transaction`:

```php
$storedDocument = null;

try {
    return DB::transaction(function () use (... &$storedDocument): ClientDocument {
        ...
        $this->files->store($document, ...);

        // Solo fijar el objetivo de compensación DESPUÉS de que store() tenga éxito.
        $storedDocument = $document;

        request transition
        audits

        return $document;
    });
} catch (\Throwable $e) {
    if ($storedDocument !== null) {
        try { $this->files->delete($storedDocument); } catch (\Throwable) {}
    }
    throw $e;
}
```

- No borra documento previo.
- No usa SHA para identificar el objetivo.
- No limpia directorio completo.
- No borra si el almacenamiento nunca tuvo éxito.
- `DocumentFileStore` sigue dueño de limpieza de fallos dentro de su propio `store()`.
- Compensación exterior dueña de fallos tras éxito de `DocumentFileStore` pero fallo de commit completo.
- Excepción original se propaga intacta.
- Nombrado físico UUID inalterado.

## 2. F1 — SECOND FILE ACTUALLY WRITTEN BEFORE FAILURE

### Defecto de prueba verificado

F1 instalaba `eloquent.saving: ClientDocument` y luego llamaba a `POST /api/documents`.
Pero `DocumentController` primero hace `ClientDocument::query()->create(...)` **antes**
de llamar a `DocumentFileStore::store()`. El listener podía lanzar durante la creación
inicial de la fila, **antes** de que el segundo archivo se escribiera. F1 podía pasar
sin ejercitar la limpieza que dice probar.

### Prueba corregida

Setup determinista mínimo:

1. Guardar documento A exitosamente vía flujo portal real.
2. Crear **segundo** modelo/row `ClientDocument` que se pase a `DocumentFileStore` directamente.
3. Instalar fallo en `save()` de ese segundo documento **DESPUÉS** de que
   `DocumentFileStore` haya escrito su archivo UUID (usando `eloquent.saving` que
   dispara dentro de `store()` después de escribir el archivo pero antes de persistir
   metadato).
4. Llamar al real `DocumentFileStore::store()` con bytes IDÉNTICOS.
5. Afirmar que la excepción propaga.
6. Afirmar documento A row sigue existiendo.
7. Afirmar documento A path físico sigue existiendo.
8. Afirmar sus bytes inalterados.
9. Afirmar que no queda archivo huérfano segundo.

Archivo modificado:
- `tests/Feature/A05/DocumentPortalFlowTest.php` (test F1 corregido)

## 3. F3 — MANTENIDO

F3 sigue verde. Prueba correctamente:

```
DocumentFileStore tiene éxito
-> luego persistencia de request lanza dentro de transacción de negocio
-> BD hace rollback
-> archivo recién escrito se elimina
-> documento/rechazado viejo sobrevive
```

Tras reestructurar `RespondToDocumentRequest`, F3 sigue en verde.

No se añade test de deadlock/commit-failure real (flaky). La auditoría independiente
verificará estructuralmente que el catch de compensación ahora envuelve `DB::transaction`
misma.
