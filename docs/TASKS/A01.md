## 1. Qué se entregó

### 1.1 Infraestructura

- Entorno Docker Compose con seis servicios: `app` (PHP-FPM), `queue`
  (consumidor), `nginx`, `node` (Vite), `postgres` 18.6 y `redis` 8.10.2.
- Imagen propia `consultora-dh/app:local` sobre `php:8.4-fpm-bookworm`, con
  `pdo_pgsql`, `pcntl`, `intl`, `bcmath`, `zip`, `redis` (phpredis) y OPcache.
  La construcción **falla** si falta alguna extensión, en lugar de fallar en
  producción.
- Comprobaciones de salud en todos los servicios de larga duración:
  - `postgres` y `redis`: comprobaciones propias de cada motor.
  - `app`: el `ping` nativo de PHP-FPM, que responde sin ejecutar PHP ni tocar
    la base de datos. Se implementó un cliente FastCGI mínimo para speaks
    (`docker/app/healthcheck.sh`).
  - `nginx`: `/healthz`, que no depende de PHP.
  - `node`: el cliente de Vite (`/@vite/client`).
- Volúmenes con nombre para PostgreSQL, Redis, `vendor/`, `node_modules/` y los
  navegadores de Playwright. Los dos últimos están fuera del montaje del
  proyecto porque leer decenas de miles de archivos pequeños a través de él es
  drásticamente más lento.
- PostgreSQL y Redis **no** se publican al host.

### 1.2 Base de datos

Migraciones de A01: `users` (con `status`, `last_login_at`,
`password_changed_at`), `password_reset_tokens`, `audit_events`, y las de
spatie para roles y permisos. Se conservan `cache` y `jobs` como respaldo
documentado de Redis; la tabla `sessions` se eliminó por ser redundante con las
sesiones en Redis.

- `users.status` es un enum de PHP **y** una restricción `CHECK` en
  PostgreSQL: ningún camino de escritura puede introducir un estado inválido.
- El correo se normaliza a minúsculas mediante un mutador del modelo, con
  índice único.
- Sin borrado lógico, por decisión explícita.
- Se crea automáticamente la base de datos de pruebas `consultora_dh_test`.

### 1.3 Autenticación y sesión

- Sesión con cookie `HttpOnly`. **Ningún token en el navegador.**
- La API se registra con el grupo `web` (no `api`), que aporta sesión y CSRF.
- `AuthenticateUser` concentra normalización, comparación de contraseña, rechazo
  de cuentas inactivas, regeneración del identificador de sesión, registro del
  último acceso y emisión de eventos.
- Respuesta **idéntica** para contraseña incorrecta, cuenta inactiva y
  dirección desconocida, más un hash señuelo para que el tiempo de respuesta
  tampoco los distinga.
- Limitación de intentos: 5 por 5 minutos, con clave `dirección + IP`.
- Recuperación de contraseña por notificación de Laravel, con `MAIL_MAILER=log`
  en desarrollo para poder ejercitar el flujo sin SMTP.
- Cierre de sesión con invalidación de sesión y token CSRF nuevo.

### 1.4 Autorización

- `spatie/laravel-permission` 8.3 con seis roles: Super Admin, Administrator,
  Operations, Collections, Support, Read Only.
- Un único permiso, `settings.view`, porque es el único que la aplicación
  exige. No se crearon permisos de negocio por adelantado.
- La comprobación es del servidor: un rol sin permiso recibe `403` aunque
  llegue directamente a la URL.

### 1.5 Auditoría

- Tabla `audit_events` de sólo inserciones (`user_id`, `action`, `ip_address`,
  `user_agent`, `metadata` JSONB, `created_at`). El modelo rechaza
  actualizaciones y borrados.
- Diez acciones: inicio y cierre de sesión, inicio fallido, rechazo por cuenta
  inactiva, recuperación solicitada y completada, cambio de nombre, de correo
  y de contraseña, y alta de administrador.
- `MetadataScrubber` redacta cualquier clave que parezca un secreto
  (`password`, `secret`, `token`, `cookie`, `authorization`, `api_key`,
  `session_id`…), a cualquier profundidad y con límite de anidamiento.
- Un único escuchas registra todos los eventos auditables: añadir una acción
  auditable es escribir una clase de evento.

### 1.6 Frontend

- Vue 3 con `<script setup lang="ts">`, Vue Router y Pinia.
- Cliente HTTP propio sobre `fetch`, con una única implementación de CSRF,
  credenciales y normalización de errores. Sin Axios.
- `ApiError` normaliza 401, 403, 404, 419, 422, 429, 500 y errores de red.
- La API expone `me()`; un 401 en cualquier petición limpia el estado y el
  guard evita ciclos de redirección.
- Componentes reutilizables: `AppWordmark`, `AppAlert`, `AppButton`,
  `AppFormField`, `AppPasswordField`, `AppEmptyState`, `AppLoading`,
  `AppModal`, `AppToasts`, y la barra lateral, la barra superior y el menú de
  usuario.
- Identidad visual en `resources/css/tokens.css`: color, tipografía,
  espaciado, radio, sombra, foco y medidas de diseño, más el puente a las
  variables de Bootstrap. Ningún componente fija un color literal.
- Bootstrap Icons e Inter **autoalojados** (paquetes npm). Sin CDN.
- Interfaz íntegramente en español, incluidos los mensajes de validación
  (`lang/es/`).

### 1.7 Pantallas

## 2. Decisiones importantes

| Decisión | Motivo |
| --- | --- |
| Monolito modular en un solo repositorio | Un servidor, un despliegue, coste operativo bajo |
| Sesión con cookie en lugar de token en `localStorage` | `HttpOnly` limita el alcance de un XSS |
| API en el grupo `web` | Es lo que hace posible la sesión con cookie y la protección CSRF |
| Sanctum | Infraestructura estándar en vez de criptografía propia |
| `fetch` en lugar de Axios | Sin dependencias, un solo lugar para CSRF y errores |
| Enum de PHP **y** `CHECK` en SQL | Dominio tipado y base de datos que no puede corromperse |
| Un solo permiso en A01 | No se crea estructura «para después» |
| Sin borrado lógico | No hay un criterio claro; se añade sólo con razón |
| Redis para sesión, caché, colas y limitadores | Infraestructura única, sin servicios de pago |
| `noeviction` en Redis | Perder una sesión silenciosamente es peor que un error visible |
| Sin capa de repositorios | Un repositorio que reescribe `Model::query()` sólo añade indirección |
| Volúmenes para `vendor` y `node_modules` | Rendimiento medible: el enlace de Docker es muchísimo más lento |

## 5. Incidencias encontradas y resueltas

Se documentan porque explican por qué el código es como es:

1. **PostgreSQL 18 cambió su diseño de datos.** El volumen debe montarse en
   `/var/lib/postgresql`, no en `/var/lib/postgresql/data`; la imagen rechaza
   arrancar de lo contrario.
2. **PHP-FPM se niega a ejecutar el pool como `root`.** El pool usa
   `www-data`; el punto de entrada prepara los directorios con permisos.
3. **PHP-FPM ignora un segundo pool `[www]`.** Los ajustes had que sustituir
   `www.conf`, no añadir un archivo nuevo. Por eso la comprobación de salud no
   funcionaba.
4. **El rol de FastCGI ocupa 2 bytes.** El primer cliente de sondeo enviaba
   `0x0100` y el pool cerraba la conexión sin responder.
5. **PHPUnit no sobrescribe variables ya presentes.** `compose.yaml` pasaba
   `APP_ENV` al contenedor, así que `<env name="APP_ENV">` de `phpunit.xml` se
   ignoraba y la CSRF seguía activa en las pruebas. Se resolvió con
   `force="true"` y retirando el paso innecesario de `APP_ENV`.
6. **El identificador de un pool vacío no es `home`.** La barra lateral buscaba
   la ruta `home` y obtenía una hoja, con lo que el menú quedaba vacío. Ahora
   busca el registro que tiene hijos y exige sesión. Hay una prueba de
   regresión.
7. **`/` y `/dashboard` generaban dos enlaces «Inicio».** Ahora `/` redirige a
   `/dashboard`, y la barra lateral muestra una sola entrada.
8. **Dos `<h1>` por página.** La barra superior repetía el título que ya
   ocupaba el encabezado principal.
9. **Specificidad CSS.** `.cdh-topbar__toggle { display: none }` se declaraba
   antes que `.cdh-icon-btn { display: grid }`, y el botón de menú aparecía en
   escritorio.
10. **El servidor de Vite anunciaba `0.0.0.0`.** Sin `server.origin`, la URL
    que se entrega al navegador no es utilizable. Y al fijar el origen, el CORS
    dejó de admitir el origen real de la aplicación.
11. **`getByLabel` también hace coincidir el `aria-label`** del botón que
    muestra la contraseña. Las pruebas de interfaz lo descubrieron por la vía
    difícil.
12. **CORS en el entorno de pruebas.** El navegador del Playwright corre dentro
    de la red de Docker, con un origen distinto al de la aplicación.
13. **El `limit` de la suite bloqueaba las ejecuciones repetidas** de extremo a
    extremo: el límite es correcto en producción, pero impedía probar. El
    script limpia los contadores antes de empezar.
14. **`Container "name"` duplicado** en `compose.yaml` impedía validar el
    archivo.
15. **`APP_DEBUG=true` expone trazas.** Es lo correcto en desarrollo; la
    pantalla de Configuración lo muestra en rojo y la documentación exige
    `APP_DEBUG=false` en producción.

## 6. Limitaciones conocidas

1. **Correo sin enviar.** `MAIL_MAILER=log` escribe el mensaje en
   `storage/logs/laravel.log`. El flujo de recuperación funciona y es
   comprobable, pero no envía correo hasta configurar un SMTP real.
2. **Sin gestión de usuarios.** A01 crea la cuenta de administrador pero no
   ofrece pantallas para darlos de alta, desactivarlos ni cambiarles el rol.
   Está previsto para un módulo posterior.
3. **La auditoría se escribe pero aún no se consulta.** No hay pantalla de
   revisión; sólo se verifica por base de datos y por pruebas.
4. **`node` es un servicio de desarrollo.** En producción se compila y nginx
   sirve `public/build`; el servicio `node` se detiene.
5. **Sin CSP activa.** Desactivada a propósito para no romper el desarrollo;
   la política de producción está escrita y documentada.
6. **`role` en el comando de alta.** Existe `--role`, pero en A01 sólo existe
   «Super Admin» hasta que se ejecute el seeder con los demás roles.

# A01-R1 — Correcciones de la revisión

## 1. Aislamiento del repositorio Git

El repositorio de Git estaba en `/mnt/c/Diomedes`, un nivel por encima del
proyecto, y sus 172 archivos estaban **únicamente en el índice, sin ningún
commit** (el repositorio padre no tenía historial). Se comprobó antes de tocar
nada:

- `git rev-list --count HEAD` → el repositorio padre **no tenía ningún commit**.
- `git log --all -- consultora-dh` → sin historial.
- Sólo había `consultora-dh/**` en el índice; ningún archivo ajeno estaba
  afectado.

Por ser el caso no destructivo descrito en la revisión, se ejecutó
`git rm -r --cached consultora-dh`, que saca los archivos del índice **sin
borrar los archivos del disco**. Después se inicializó un repositorio nuevo
dentro de `consultora-dh/`, sobre la rama `main`. `git rev-parse
--show-toplevel` devuelve exactamente `/mnt/c/Diomedes/consultora-dh`.

El repositorio padre quedó intacto: sin commits, con el índice vacío y su
`.git` sin tocar.

## 2. `.env.example` reconstruido

El archivo era el esqueleto de Laravel sin modificar: `APP_NAME=Laravel`,
`DB_CONNECTION=sqlite`, `SESSION_DRIVER=database`, `QUEUE_CONNECTION=database`,

variables de AWS que el proyecto no usa. No describía la arquitectura real.

Se reescribió para reflejar la arquitectura efectiva: aplicación, puertos,

## 3. `POSTGRES_ROOT_PASSWORD` eliminada

La imagen oficial de PostgreSQL no usa esa variable. Se eliminó de
`compose.yaml`, `.env.example`, `README.md`, `docs/SECURITY.md` y

## 4. Rol de aplicación sin superusuario

Antes, `POSTGRES_USER=consultora_dh` creaba un **superusuario** de PostgreSQL y

Ahora hay dos roles con propósitos separados:

| Rol | Variables | ¿Superusuario? | Uso |

| `consultora_dh_app` | `DB_USERNAME` / `DB_PASSWORD` | **No** | Laravel, incluidas las migraciones |

Se recreó **sólo** el volumen de PostgreSQL de Consultora DH para validar el

Comprobado: `is_superuser = off`, migraciones y semillas correctas, y el rol de
la aplicación **no** puede crear roles ni bases de datos.

## 5. Rotación del `remember_token`

Se añadió `App\Domain\Users\Actions\RotateRememberToken`, que regenera el token
con `Str::random(60)`. Se invoca en los dos caminos:

- cambio de contraseña desde el perfil (`ProfileController`);
- restablecimiento de contraseña (`AuthController`).

Sin criptografía propia: es el mecanismo `remember_token` del framework. Cuatro
pruebas nuevas lo cubren, y las de autenticación existentes siguen pasando.

## 6. Evento `Login` duplicado eliminado

`Auth::login()` ya despacha `Illuminate\Auth\Events\Login`. `AuthenticateUser`
lo despachaba **otra vez** a mano, de modo que todo escucha se ejecutaba dos
veces por inicio de sesión. Se eliminó el despacho manual y se conservó el
evento de dominio `AuthenticationSucceeded`.

Tres pruebas nuevas demuestran que el evento del framework se emite
**exactamente una vez**, y cero veces cuando el intento se rechaza o la cuenta
está inactiva.

## 7. Cabeceras de confianza (`Host`)

`App\Http\Middleware\TrustHosts` (subclase del `TrustHosts` del framework)
acepta únicamente los hosts de `config/security.php` y responde **400** al
resto. Se activa **también en desarrollo**, a diferencia del comportamiento por
defecto del framework, para que el control exista siempre y sea verificable.

La lista se compone de `localhost` y `127.0.0.1` con cualquier puerto, los
nombres de servicio de Docker, y `TRUSTED_HOSTS` (obligatorio en producción,
vacío a propósito para no adivinar un dominio no definido). Nueve pruebas.

# A01-R2 — Endurecimiento final de seguridad y autenticación

**Estado:** completada. Última pasada de corrección sobre la base de A01. No se
implementó nada de A02.

## 1. Hosts de confianza: en producción falla cerrado

### El problema

`config/security.php` mezclaba hosts de desarrollo y de producción: `localhost`,
`127.0.0.1`, `nginx` y `app` estaban **siempre** presentes, también en
producción. Y `TRUSTED_HOSTS` se documentaba como una lista de nombres literales
pero sus valores se pasaban **sin escapar** a Symfony, que los usa como
expresiones regulares: `portal.consultoradh.com` habría coincidido también con
`portalXconsultoradhXcom`.

### La corrección

`app/Support/Security/TrustedHostConfiguration.php` decide qué hosts existen y
convierte cada entrada en un patrón literal.

| Entorno | Lista |
| --- | --- |
| `local`, `testing` | `localhost`, `127.0.0.1`, `[::1]`, `nginx`, `app` + lo configurado |
| `production`, `staging`, `ci`, cualquier otra | **sólo** lo configurado en `TRUSTED_HOSTS` |

`staging` se trata como producción a propósito: un entorno de pruebas que acepta
`localhost` es un entorno que se promueve con el control desactivado.

**Nombres literales, no expresiones regulares.** Cada entrada se normaliza a
minúsculas y se escapa con `preg_quote()`, con anclas:

```
TRUSTED_HOSTS=portal.consultoradh.com,www.consultoradh.com
  →  ^portal\.consultoradh\.com$
  →  ^www\.consultoradh\.com$
```

Esto no es sólo convención. Symfony reconoce los patrones con la forma
`^escapado$` y los resuelve **con una tabla hash, sin pasar por el motor de
expresiones regulares**. Una entrada que no sea un nombre de dominio —`.*`, `^`,
`a|b`, `[a-z]+.io`, `*.consultoradh.com`, `http://…`, `host:puerto`— se
**descarta antes de convertirse en patrón**, y se informa en el log. Por eso un
valor del entorno no puede inyectar sintaxis de expresión regular. Los
subdominios con comodín quedan para una opción futura y explícita.

### Fallo cerrado

`App\Http\Middleware\TrustHosts` sobrescribe `handle()`. Con lista vacía **no**
llama a `Request::setTrustedHosts([])`, porque una lista vacía en Symfony
significa «no hay nada que comprobar» y por tanto **acepta cualquier host**.
Lanza `TrustedHostsNotConfigured` y la aplicación responde **503** con el código
`trusted_hosts_not_configured`; el motivo exacto queda en el log.

Sin lista: 503. Con lista: 400 para lo que no esté en ella. Nunca «aceptar
`localhost` en producción».

## 2. Límites de intentos separados por política

El problema: `login`, `forgot-password` y `reset-password` compartían los
contadores `auth-attempt` y `auth-account`. Bastaba pedir restablecer la
contraseña en bucle para impedir que un administrador iniciara sesión, sin
adivinar una sola contraseña.

Ahora hay tres políticas independientes, cada una con dos dimensiones:

| Política | Se aplica a | Por IP | Por cuenta |
| --- | --- | --- | --- |
| `login-attempt` / `login-account` | `POST /api/auth/login` | 20 / 5 min | **30** / 15 min |
| `recovery-attempt` / `recovery-account` | `POST /api/auth/forgot-password` | 10 / 15 min | 5 / 15 min |
| `reset-attempt` / `reset-account` | `POST /api/auth/reset-password` | 10 / 15 min | 5 / 15 min |

**Por qué 30 y no 10 por cuenta.** Con 10, tres reintentos y un compañero
compartiendo la dirección de la oficina agotaban el presupuesto de un
administrador durante un cuarto de hora. El límite se convertía en un arma
contra el usuario legítimo sin ganancia alguna: un atacante que quisiera bloquear
una dirección conocida tendría que superar además el límite por IP, y eso exige
varias máquinas. Con 30 sigue obteniendo 30 contraseñas por cuarto de hora, que
no es una vía viable contra 12 caracteres con mayúsculas, minúsculas y números,
y el error humano corriente deja de consumir el presupuesto. El límite por IP
sigue en 20/5 min porque es el que un atacante no puede subir sin moverse de
máquina.

La recuperación puede ser **más estricta** que el inicio de sesión, nunca al
revés: cada petición aceptada cuesta un correo saliente y, en el
restablecimiento, un token. Se suma al *throttle* del propio *password broker*
(60 s), que sigue siendo el límite más estrecho sobre correos repetidos a una
misma dirección.

## 3. `--password` eliminado de `create-admin`

No está desactivado: **no existe**. Symfony rechaza el argumento antes de que el
comando se ejecute. Una contraseña pasada como argumento queda en el historial
del shell, en `ps` para cualquier usuario de la máquina y en el log de la
herramienta que lo ejecute.

| Situación | Mecanismo |
| --- | --- |
| Interactivo | Prompt oculto `secret()` |
| Automatizado | `CONSULTORA_DH_ADMIN_PASSWORD` + `…_CONFIRMATION`, leídas como par |

Las únicas opciones que quedan son `--name`, `--email` y `--role`. Las pruebas
sumintran la contraseña por entorno y la limpian en `afterEach`.

## 4. Una cuenta inactiva pierde el acceso que ya tenía

Rechazar una cuenta inactiva **al iniciar sesión** no bastaba: una sesión abierta
mientras estaba activa seguía funcionando hasta que caducaba la cookie, que es
lo contrario de lo que espera quien suspende a alguien.

`App\Http\Middleware\EnsureUserIsActive`, aplicado como `user.active` en el
grupo autenticado de `routes/api.php`, comprueba el estado **en el servidor** en
cada petición. Al encontrar una cuenta inactiva: cierra sesión, la invalida,
renueva el token CSRF, responde 401 con el cuerpo habitual de «no autenticado»
(sin explicar que la cuenta está suspendida) y registra
`auth.session.rejected_inactive`.

**Una sola fila de auditoría por transición**, porque al invalidar la sesión
desaparece el usuario y las peticiones siguientes ya no tienen a nadie que
registrar. Reactivar la cuenta **no** restituye la sesión anterior: el acceso se
cortó, no se pausó.

El valor `user.status` de la interfaz es sólo presentación; nunca se consulta
para decidir.

## 5. Verificación del correo al cambiar la dirección

`users.email_verified_at` se pone a `null` cuando la dirección cambia **de
verdad**, y se conserva cuando no. A01 no exige verificación, así que esto no
cambia nada visible; lo que evita es que la columna afirme haber verificado una
dirección que nadie comprobó.

La comparación se hace sobre el valor normalizado: `User::email()` pasa a
minúsculas y recorta al asignar, así que reenviar la misma dirección con otra
capitalización **no** es un cambio.

## 6. `REDIS_PASSWORD` documentada como obligatoria

`.env.example` decía «vacío en desarrollo», pero `compose.yaml` exige
`${REDIS_PASSWORD:?…}` y se niega a arrancar. La redacción ahora dice
**obligatoria en desarrollo y en producción**, con la explicación de qué expone
sin ella. No se debilitó la autenticación de Redis.

## 7. Limpieza de Composer

`post-create-project-cmd` se eliminó. Es un gancho que **sólo** se ejecuta en
`composer create-project`, es decir al crear el proyecto desde una plantilla; en
este repositorio, que ya **es** el paquete raíz, nunca puede dispararse. Contenía
además `touch('database/database.sqlite')`, que pertenece al esqueleto de
Laravel con SQLite y no corresponde a una arquitectura sólo PostgreSQL.

**Lo que se revisó y NO se tocó:**

- `dev` invoca `php artisan dev`, que **sí existe** (comando de desarrollo de
  Laravel). Funciona.
- `post-autoload-dump`, `post-update-cmd`, `post-root-package-install`,
  `pre-package-uninstall`: scripts de ciclo de vida que **sí** se ejecutan aquí.
  No se modificaron.
- `composer validate --strict` sigue pasando.

Queda una referencia a `database/database.sqlite` como valor por defecto de la
conexión `sqlite` en `config/database.php`, que es el esqueleto de Laravel y no
se usa: `DB_CONNECTION` es `pgsql` y el valor no aplica. No se tocó para no
ampliar el alcance.
