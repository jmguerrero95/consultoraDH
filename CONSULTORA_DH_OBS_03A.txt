ROOT_CAUSE=El sistema no tenía mecanismo de idempotencia para el registro de pagos. Un doble clic, timeout o reintento HTTP podía registrar el mismo pago varias veces, ya que no existía ninguna clave que identificara el intento de registro.

FIX=Se implementó una clave de idempotencia opcional por intento de registro, garantizando atomicidad en PostgreSQL:
1. Nueva columna `idempotency_key` (VARCHAR 255, nullable) en la tabla `payments` con restricción única parcial (WHERE idempotency_key IS NOT NULL)
2. Campo opcional `idempotency_key` en `StorePaymentRequest` (validación string max:255)
3. Lógica en `PaymentController::store()`: si la clave ya existe en la BD, devuelve el pago original (200); si no, registra el nuevo pago aprovechando la restricción única para concurrencia
4. Lógica en `ManagePayments::register()`: almacena la clave en la inserción y verifica antes de commit, garantizando que dos requests concurrentes con la misma clave solo produzcan un pago
5. El campo `idempotency_key` se incluye en la respuesta JSON para que el frontend lo conserve y lo reutilice en nuevos intentos

CRITERIOS CUMPLIDOS:
1. ✅ Misma clave + mismos datos → devuelve el pago original (200), sin crear otro ni repetir efectos
2. ✅ Misma clave + datos distintos → 409, sin modificar registros
3. ✅ Claves diferentes permiten pagos legítimos idénticos, conservando la advertencia `possible_duplicate` y la confirmación manual `confirm_duplicate`
4. ✅ La clave se conserva ante errores de red y durante `confirm_duplicate`; el frontend debe almacenarla y reenviarla en nuevas operaciones
5. ✅ Garantía atómica en PostgreSQL mediante restricción única, sin depender de búsquedas previas ni bloqueos solo en JavaScript
6. ✅ Compatibilidad con consumidores antiguos: la clave es opcional; sin ella, el flujo de `possible_duplicate` y `confirm_duplicate` se comporta exactamente como antes
7. ✅ Sin mecanismos genéricos de idempotencia para toda la plataforma; solo para `POST /api/payments`
8. ✅ Sin nuevas dependencias: solo una columna en la tabla `payments` y lógica en PHP existente
9. ✅ Transacciones, bloqueos, eventos (PaymentCreated), auditoría, permisos y comportamiento de pagos parciales conservados
10. ✅ El frontend (PaymentListPage.vue) ya mostraba la advertencia `possible_duplicate`; ahora el backend la evita al reutilizar la clave
